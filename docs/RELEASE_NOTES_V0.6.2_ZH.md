# STS2 LAN Connect v0.6.2 正式版发布说明

发布日期：2026-09-19

> 状态：**正式版（stable）**。客户端与 lobby-service 同步定为 `0.6.2`。
> 分发：GitHub Release（客户端 `sts2_lan_connect-release.zip` + 服务端 `sts2_lobby_service.zip`）。本版会同步更新 Steam 创意工坊「游戏大厅」条目（`3749766330`）。

`0.6.2` 收敛了 `0.6.2-alpha.1`、`0.6.2-alpha.2` 两个测试候选，以及其后的续局恢复修复、公共节点发现修复与大厅主题系统。核心是把 `native_bus_v1` 的消息 ID 从「本机下标」改成 **按对端寻址**：`0.6.1` 隐含要求两端的联机消息注册表完全相同，任何一端多装一个注册消息的第三方 MOD（跨端尤其常见）就会被指纹门禁拒之门外；`0.6.2` 之后两张表无需任何关系。此外重做了选服列表的排序与服务端版本标注，修复了「取消恢复后再也恢复不了」的续局问题与公共节点列表长期停更的问题，并为大厅界面引入了可切换的主题系统。

## 一、native_bus 消息 ID 改为按对端寻址（v0.6.2 的主线）

- `0.6.1` 起用户反馈「手机只能和手机连、电脑只能和电脑连」，双向复现 HTTP 409 `lan_registry_fingerprint_mismatch`（提示「双方的联机消息注册表不一致」）。两端客户端版本、游戏版本、游戏程序集、BaseLib / RitsuLib、wire_cache 签名完全一致，仍被拒绝。
- **根因**：`native_bus_v1` 的 `typeId` 是**接收方本地消息表的下标**，由游戏按本机 MOD 集合排序分配。`0.6.1` 发送时写的是自己的下标，隐含「两端表必须相同」，并用 registry fingerprint 全表哈希门禁强制这一点。任何一端多装一个注册 `INetMessage` 的第三方 MOD（本次事故为安卓端 `Map Enhance Mod`）即令全表不一致——而该类 MOD `affects_gameplay:false`，对既有三项 MOD 检查完全隐形。
- **方案**：发送时改写**接收方声明的下标**。发送端线头字节与帧内 `localTypeId` 均写对端 id；外层帧版本 `ver` 由 `1` 升为 `2`（`ver != 2` ⇒ `lan_native_frame_invalid` 结构化拒绝，不会误读）。接收路径校验不变。
- 对端 id 经服务端透传：建房 offer / join 请求 / join 响应（`hostNativeBusTypeId`）/ 控制通道 envelope（`peerNativeBusTypeId`），轨道与已验证的 `protocolFlowNonce` 完全一致；中继保留字段防伪造。取不到有效对端 ID 一律结构化失败 `lan_type_id_mismatch`，绝不静默回退本机 ID。
- **撤除 fingerprint 主门禁**：`lan_registry_fingerprint_mismatch` 不再拒绝加入，指纹降级为诊断值（仍必须携带且格式合法，`lan_registry_fingerprint_required` 保留）；`/mod-preflight` 不再据此快速失败。tail_v1 创建与加入新增必填 `nativeBusTypeId`（整数 0-255），缺失 / 越界复用 `lan_registry_fingerprint_required`（文案区分）。
- `native_bus_v1` 的 `minimumClientVersion` 升至 `0.6.2-alpha.1`：`0.6.1` 及更早客户端加入新协议房间会在服务端就得到明确的 426 `lan_client_version_too_old` 升级提示，而不是在 `ver` 校验处才失败。
- 同时移除了 tail 握手中遗留的「双方 RitsuLib 安装状态必须相等」校验，使 `0.6.1` 起宣称的「新协议房间不关心 RitsuLib」在冻结选择的校验路径上真正生效。
- 启动自检得出终局裁决后补打一次 `native_bus: ready local_type_id=… registry_fingerprint=…` 诊断行（此前该行从不出现）。

## 二、选服列表排序重做与服务端版本徽章

- `0.6.x` 的选服列表按「置顶 → 最近连过 → 延迟档（500ms/2000ms）→ 地址字符串」排序：「最近连过」是死条件（生产代码从不写入），延迟只分三档，完全不区分服务器版本，而 `0.6.x` 客户端**根本无法使用** `0.6.0` 以前的 lobby-service；每收到一批探测结果还会全量重排，列表在刷新过程中来回跳动。
- **新排序规则**（自上而下逐级比较）：置顶（魔仙堡继续置顶）→ 可达性（可达永远在不可达 / 探测中之前）→ 服务端大版本档 `major.minor`（降序，未知最低；`0.6.2`、`0.6.1`、`0.6.0` 同属 `0.6` 档）→ 真实延迟（升序，精确毫秒，每次探测取两次采样的较小值）→ 地址（保证结果确定）。
- **服务端版本识别**：新增公开字段 `serviceVersion`（`/probe` 的 `capabilities.serviceVersion` 与 `/peers/metrics` 的 `serviceVersion`）。未升级的服务器靠 `/probe` 能力字段推断版本档：`dualProtocolApiVersion ≥ 1` ⇒ `0.6.x（推断）`；`modSyncProtocolVersion ≥ 1` 或 `serverChatVersion ≥ 1` ⇒ `0.5.x（推断）`；只有 `{"ok":true}` ⇒ `0.4.x 或更早（推断）`。`/probe` 失败、非 JSON、`ok:false`、显式 `capabilities:null` 一律视为「未知」；metrics 报告的合法版本永远优先于推断。
- **UI 标注**：版本档低于 0.6 的行显示红色徽章「服务端版本过旧」，tooltip 追加「该服务器的 lobby-service 低于 0.6.0，当前客户端无法在此创建或加入房间。」（只标注，不禁止点击；未知与 ≥0.6 不显示徽章。）
- **列表不再跳动**：刷新过程中每批结果只更新行内数据（保持当前顺序、新条目追加末尾），全部结果到齐后只做一次最终重排。另新增结构化日志（`refresh:` / `render:` / `order:` / `closed:`，带窗口与轮次标识）便于定位。

## 三、续局与恢复修复

- 修复**多人存档恢复房间后取消、再次点击恢复无效、必须重启游戏才能再恢复**的问题。载入页面每次关闭时清理本轮发布状态；快速取消再进入时，旧请求结束后会自动重新尝试当前这次恢复。
- **已取消的提示框结果不再写入存档绑定**：「保存到大厅还是 LAN」这类对话框如果在其所属载入页面关闭之后才被确认，该结果直接丢弃，既不会覆盖新打开的提示，也不会污染下一次恢复的通道选择。
- **迟到的建房响应不再挂载已断开的主机**：注册完成后如果本地连接已经断开（玩家已取消并重开），客户端会立即删除刚注册的房间，并以「续局已取消，请重新恢复房间。」结束这次尝试，不再让旧会话冻结在新会话之上、留下一个没人能进的幽灵房间。
- 上述修复在 Mac + Android 模拟器上验证：首战 E2E、同一进程连续三次恢复（其中两次取消）、原角色重新加入与退出恢复均通过；「重开一局」S/L 在奖励阶段与战斗中途补测均通过，房间管理面板的重开 S/L 也已在 Mac 与 Android 上复测。详见 `docs/ALPHA1_RESUME_QA_20260912.md`。

## 四、大厅主题系统

- 大厅界面右上角设置齿轮旁新增**调色盘按钮**，可随时切换主题；选择持久化保存（`LobbyThemeId`），下次进入游戏沿用。
- 三套主题：
  - **街机复古**：即 `0.6.1` 起的像素风外观，仍是默认值，不改变任何既有习惯。
  - **午夜玻璃**：深色圆角毛玻璃面板，带亮边、内折射带与外发光环，品牌标与「创建房间」使用紫色渐变，背景为夜空图。
  - **SaaS 简洁**：浅色扁平外观，房间标签按语义配色。
- 主题覆盖大厅总览、公告轮播、选服窗口、选择对话框、房间管理面板与大厅风格聊天；局内 HUD 有意保持原样，不随主题变化。
- **点击房间卡片现在立即高亮**：此前点击会先抢到焦点、在 `gui_input` 之前就改掉了选中 id，导致重建被跳过，要等到下一次自动刷新才看到高亮。所有主题下的房间卡片同时新增了悬停反馈。

## 五、公共节点发现修复

- 公共节点列表（Cloudflare discovery worker）自 2026-08-30 起实际停更 13 天，期间新加入的大厅在客户端里根本看不到。
- **根因**：Cloudflare Workers 的 `fetch()` 访问裸 IP 源站会被 Cloudflare 自身以 HTTP 403 / error 1003 拒绝，请求根本到不了源站。聚合器只从 `seeds[:5] + previous[:5]` 里挑采样对象，当唯一的域名种子下线后，每一轮都只抽到 IP 直连节点、什么都取不到，24 小时留存耗尽，空结果保护又把 `peers:active` 冻在原地。
- **修复**：采样池扩大为全部种子 + 全部历史条目，并跳过 IP 直连地址（先种子、再随机域名条目，最多 8 个）；`/peers/metrics` 的退出探测同样跳过 IP 直连。IP 直连的大厅仍可经域名节点的 `/peers` 转述进入列表，不会消失。运维侧已把 KV `peers:seeds` 改写为四个域名节点。

## 六、版本与升级

| 组件 | 0.6.2 | 上一个正式版 |
|---|---|---|
| 客户端 MOD | `0.6.2` | `0.6.1` |
| lobby-service | `0.6.2` | `0.6.1` |

**玩家**

1. 下载 `sts2_lan_connect-release.zip`，用包内一键脚本或手动覆盖安装；也可直接在 Steam 创意工坊订阅「游戏大厅」。
2. 安装或更新后必须**完整重启游戏**。
3. **同一房间所有成员必须统一使用客户端 `0.6.2`**。`0.6.1` 及更早客户端加入 `0.6.2` 新协议房间会被服务端以 426 `lan_client_version_too_old` 拒绝并提示升级；`0.6.2-alpha.1` / `0.6.2-alpha.2` 客户端仍可加入（tail 房间 `minimumClientVersion` 保持 `0.6.2-alpha.1`）。
4. 新协议房间不再要求两端的 MOD 集合或消息注册表一致，跨平台（PC ↔ 安卓）与「一边多装一个第三方 MOD」都可以正常同房。
5. 兼容模式 `compat_4_5_v1` 房间完全不受影响，继续禁止 RitsuLib；direct-IP 直连仍只支持兼容模式。

**服主**

- lobby-service `0.6.2` 与 `0.6.1` **不等价**：新增 `nativeBusTypeId` 四段透传与 `serviceVersion` 公开字段，`0.6.2` 客户端需要 `0.6.2`（或 `0.6.2-alpha.x`）服务端才能建 / 加新协议房间，请务必升级。
- 本 Release 附带 `sts2_lobby_service.zip`，**非 pre-release**：已开启自动更新的节点会自动升级到 `0.6.2`。手动路径见 `docs/STS2_LOBBY_DEPLOYMENT_GUIDE_ZH.md`。
- 升级后 `/probe` 与 `/peers/metrics` 会公开 `serviceVersion`（版本号本就在免登录管理页公开，不扩大信息暴露面）；不升级的节点会在玩家的选服列表里被推断为旧版本档并排在后面。

## 八、已知限制

- direct-IP 直连只支持兼容模式；LAN 建房 / 直连 / 仅 LAN 续局尚未支持新协议。
- 局内 HUD 不随大厅主题变化（有意为之）。
- 怪物目标引用（富聊天）仍未开放。
- 服务器频道聊天历史只存在于单个节点的进程内存中，重启即清空；房间聊天不保存历史。
- 历史 `0.3.x`-`0.5.x` 客户端与 `0.6.2` 的真实互通不在测试与发布门禁范围内。

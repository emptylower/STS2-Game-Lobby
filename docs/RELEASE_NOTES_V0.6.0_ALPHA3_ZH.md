# STS2 LAN Connect v0.6.0-alpha.3 测试版说明

发布日期：2026-08-16

这是客户端 RitsuLib 联机时序修复测试版。客户端升级到 `0.6.0-alpha.3`；lobby-service 继续使用 `0.6.0-alpha.1`，无需重新部署服务端。同一房间的所有玩家必须统一客户端、游戏版本和 RitsuLib 启用状态，更新后完整重启游戏。

## 本轮修复

- 修复 `0.6.0-alpha.2` 仍会卡在“等待初始游戏信息”的问题。现场日志确认 RitsuLib 在 `ConnectToHost` 之前观察客户端网络服务，并把会话永久绑定到尚未分配的 `netId=0`。
- 客户端现在把 Ritsu sidecar 初始化拆成准备和激活两个阶段：连接前仅注册公开 carrier 并准备 ticket 对应的可信协议流；ENet 连接成功、真实玩家 ID 已分配后，才首次绑定 RitsuLib 会话并标记主机可达。
- 修复 SL/房主重开时加入者自动重连没有启动的问题。现场日志显示重连任务已经排队并成功返回主菜单，但再次打开的是缓存多人子菜单，不会重复触发 `_Ready`；现在导航完成后会显式唤醒待处理重连。
- 保留 `alpha.2` 的房主首包延迟发送、SL/读档协议身份复用和建房弹窗改进。

## 测试边界

- 本版只改客户端，不改变 lobby-service API、房间协议、Relay 或部署配置。
- `tail_v1` 的 RitsuLib 房间仍要求所有参与者启用 RitsuLib；有/无 RitsuLib 混合组合会在 ticket 和 transport 前拒绝。
- Android 上 RitsuLib v0.5.12 自身初始化失败仍属于外部限制；本修复针对 Windows 日志中已完成 RitsuLib 启动、但联机首包无法进入正确会话的路径。

## 复测要点

- 两端都安装并启用 RitsuLib v0.5.12，使用客户端 `0.6.0-alpha.3` 和同一游戏版本加入 `tail_v1` 房间。
- 客户端日志中的 RitsuLib `Session bound` 应显示真实非零 `netId`，不应再出现 `netType=Client, netId=0`。
- 加入者应在握手后收到初始游戏信息并进入联机大厅；若仍失败，请同时提交房主与加入者的完整 `godot.log`。
- 房主执行重开后，加入者应自动返回主菜单、进入多人子菜单并重新加入新发布的续局房间；加入者没有本地多人存档属于正常情况，不应阻止按原玩家 ID 重连。

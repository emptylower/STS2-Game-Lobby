# STS2 LAN Connect v0.6.2-alpha.2 发布说明（内部预览）

- 日期：2026-09-13
- 版本：`0.6.2-alpha.2`（客户端 MOD 与 lobby-service 同步；本版不改 wire 协议，tail 房间 `minimumClientVersion` 保持 `0.6.2-alpha.1` 不变）
- **本版为 pre-release 预发布（仅 GitHub），不更新 Steam 创意工坊；当前正式版仍为 `0.6.1`。**

## 一、修的是什么：选服列表排序不反映服务器新旧与真实延迟

0.6.x 的选服列表按「置顶 → 最近连过 → 延迟档（500ms/2000ms）→ 地址字符串」排序：

- 「最近连过」是死条件，生产代码从不写入，只可能来自旧缓存文件；
- 延迟只分三档，同档内按地址字符串排，与真实毫秒无关；
- 完全不区分服务器版本——而 0.6.x 客户端**根本无法使用** 0.6.0 以前的 lobby-service
  （缺少 `protocolSelection`，加入/建房直接报 `lan_protocol_version_mismatch`）；
- 每收到一批探测结果就全量重排，列表在刷新过程中来回跳动。

线上实际分布（2026-09-13）：0.6.2-alpha.1 ×1、0.6.1 ×2、0.5.4 ×1、0.5.1 ×5、0.4.0 ×3、读不到 ×2。
旧排序把大量 0.4/0.5 服务器排在 0.6 服务器前面，用户点进去才发现用不了。

## 二、新排序规则

自上而下逐级比较：

1. **置顶**：魔仙堡（`http://101.35.217.99:8788`）继续置顶，行为不变；
2. **可达性**：可达服务器永远排在不可达/探测中的服务器之前；
3. **版本档**（降序）：服务端大版本档 `major.minor` 越新越靠前；`0.6.2-alpha.1`、`0.6.1`、`0.6.0` 同属 `0.6` 档；
4. **真实延迟**（升序）：同档内按精确毫秒（每次探测取两次采样的较小值）从低到高；
5. **地址**：毫秒相同时按地址排序，保证结果确定。

不再使用延迟容差档；列表不跳动由下述「每轮只重排一次」机制解决。

## 三、服务端版本识别

- **新增公开字段 `serviceVersion`**：`/probe` 的 `capabilities.serviceVersion` 与 `/peers/metrics` 的
  `serviceVersion` 均返回 lobby-service 版本号（未升级的旧服务端无此字段，不扩大信息暴露面——版本号本就在免登录管理页公开）。
- 未升级的服务器靠 `/probe` 能力字段推断版本档：`dualProtocolApiVersion ≥ 1` ⇒ `0.6.x（推断）`；
  `modSyncProtocolVersion ≥ 1` 或 `serverChatVersion ≥ 1` ⇒ `0.5.x（推断）`；只有 `{"ok":true}` ⇒ `0.4.x 或更早（推断）`。
- `/probe` 请求失败、非 JSON、`ok:false`、显式 `capabilities:null` 一律视为「未知」，未知不参与标注也不参与档位。
- metrics 报告的合法 `serviceVersion` 永远优先，`/probe` 推断不得将其覆盖。

## 四、UI 标注与列表稳定性

- 版本档低于 0.6 的行显示红色徽章「**服务端版本过旧**」；tooltip 追加
  `服务端版本：…` 与说明「该服务器的 lobby-service 低于 0.6.0，当前客户端无法在此创建或加入房间。」
  （不禁止点击，只标注；未知与 ≥0.6 不显示徽章。）
- 刷新过程中每批结果只更新行内数据（`resort=false`，保持当前顺序、新条目追加末尾）；
  全部结果到齐后只做一次最终重排，列表不再来回跳动。
- 新增结构化日志（`refresh:` / `render:` / `order:` / `closed:`，带窗口与轮次标识），供 E2E 自动核对最终排序与不跳动断言。

## 五、兼容性

| 组合 | 结果 |
|------|------|
| 旧客户端 + 新服务端 | 旧客户端忽略新增 `serviceVersion` 字段，行为不变 |
| 新客户端 + 0.6.2-alpha.2 服务端 | 读取 `serviceVersion`，显示精确版本 |
| 新客户端 + 0.6.0～0.6.2-alpha.1 服务端 | `/probe` 推断为 0.6 档 |
| 新客户端 + 0.5.x / 0.4.x 服务端 | 推断为 0.5 / 0.4 档，标注「服务端版本过旧」 |
| 新客户端 + `/probe` 失败但延迟探测通 | 有 metrics 版本则用之，否则未知，排可达组末尾，不标注 |
| Cloudflare Worker / KV / 节点网络 | 完全不变 |

请求量（每台每轮）：`/peers/health` 最多 2 次（失败回退时 `/probe` 最多 2 次）；`/peers/metrics` 1 次、`/probe` 0～1 次，均为极小 JSON。

## 六、升级与回滚

- 客户端覆盖安装即可；服务端部署 `lobby-service` 0.6.2-alpha.2 并重启（自动更新不接受 pre-release，需手动升级）。
- 不改任何 wire 协议与最低版本要求：alpha.1 客户端仍可进入 tail 房间，与 0.6.2-alpha.1 服务端互通。
- 回滚：卸载 0.6.2-alpha.2 客户端、重装 0.6.2-alpha.1 或 0.6.1 即可，无数据迁移。

## 七、验收范围

- ✅ 自动测试：客户端单测 1,216 通过（1 项既有跳过）；GdUnit 运行时 394 通过（含「服务端版本过旧」徽章用例）；大厅服务端 613 通过；Release 构建、0.107.1 类型加载与打包校验通过。
- ✅ 真机 E2E（Mac，游戏 0.111.0）：3 轮完整刷新的排序与不跳动断言共 125 项全部通过；魔仙堡始终置顶；0.5.x / 0.4.x 服务器显示「服务端版本过旧」；本地 0.6.2-alpha.2 服务端显示精确版本；连续快速刷新、打开后立即关闭均无残留重排；从魔仙堡进入大厅正常。
- 发布包中的客户端 DLL 由打包脚本按既有流程构建；真机 E2E 使用的是同一源码的 Release 构建。

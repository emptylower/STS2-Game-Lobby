# STS2 LAN Connect v0.6.5 开发计划

本文以当前开放事项与本地候选证据安排下一轮工作。`v0.6.5` 为建议版本号，尚未指派版本或确定发布日期。

## 当前基线与范围

- 正式客户端为 `v0.6.4`，大厅服务端为 `0.6.3`。GitHub ZIP 和包内 DLL 的 SHA-256 均与发布记录一致，本地候选待发布。
- 计划覆盖全部 10 条当前开放的 GitHub Issue，以及尚未稳定复现的多人重开顺序依赖。
- 正式版的游戏 `0.113.1` 验证包括 ABI 与编解码，Android 实机反馈来自 `0.113.0`。
- 本轮先完成续局、名册与开局稳定性，再验收昵称和输入交互。协议默认值调整依赖稳定性通过，较大的体验扩展后移。

## P0 联机稳定性

### 多人重开顺序依赖

多人重开疑似要求按首次入房顺序加入，目前未稳定复现。正式版的原生续局应答与 Tail 名册顺序不一致时会拒绝加入，需用复测确认用户反馈是否由这条校验引起。

- [ ] 使用同一份三人存档、固定玩家身份，分别运行正式 `v0.6.4` 与本地候选，保存版本、构建标识和双方日志。
- [ ] 分别测试手动加载存档与原生房间管理重开，保留同一存档以比较两条路径。
- [ ] 按存档中的实际槽位安排原序与逆序重进，逐人记录首次入房顺序、存档槽位和实际重进顺序。
- [ ] 每组均核对玩家恢复到原角色与原槽位，完成开局并再次保存。
- [ ] 若只有原生重开失败，单独追查身份延续、自动重连与旧会话清理，补针对该路径的回归。

### #48 同成员离开重进后开局

- [ ] 固定新建准备房场景，玩家离开后重新加入，最终成员集合保持相同，然后开始游戏。
- [ ] 对照权威名册版本与发送日志，确认 pending Tail 在 writer reset 前后的扩展发送情况，复现成员相同却出现 revision gap 的链路。
- [ ] 修正扩展帧生成、发送和清理的时序，验收扩展帧按序传递且名册版本检查仍有效。
- [ ] 覆盖连续离开重进、不同 ready 时机和桌面／Android 发送路径，验证重复消息与旧更新不会推进当前状态。

### #46 减员后立即开局

本地候选已实现认证原生离开通知与名册更新，已有自动化验收记录，完整多人及混版仍待验证。本项与 #48 的同成员重进分别验收。

- [ ] 在 3→2、8→7 场景分别测试主动退出、踢人和断线，剩余玩家立即开局。
- [ ] 测试全部 ready 后减员、连续减员、同槽位替补和同一玩家重进，确保旧离开事件与延迟更新不会误删新成员。
- [ ] 核对离开来源、阶段、身份、槽位和权威版本仍受检查，运行中离线角色不套用准备房减员规则。
- [ ] 验证 2→1 仍按协议拒绝一人 Tail 快照，并在发布说明列明此限制。

### #44 兼容与容量验收

普通加入相关修复已经随 `v0.6.4` 交付，余项按回归和适配验收推进。本地候选另含续局应答排序与构造兼容两项独立改动。

- [ ] 验证 LoadJoin 发送副本按实际存档槽位排列，原生 body 与 Tail 一致，玩家标志随身份保留，大厅共享列表不被修改。
- [ ] 验证新版五参容量构造优先匹配并回退旧四参，不能由补丁挂载成功推断满员联机通过。
- [ ] 分别记录游戏 `0.113.0`、`0.113.1` 和 `0.111.0` 的兼容结果，覆盖第 5／8 人加入和满员拒绝，验证极速、恐惧、自定义准备页及每日模式的容量限制。
- [ ] 分开记录同候选、旧房主配新客机、新房主配旧客机与 PC／Android 组合，发现限制时明确支持范围。

## P1 昵称与交互验收

### 昵称设置

本地昵称流程已经实现，已有构建零警告／错误、隔离 Godot 24／24 与单元测试 70／70 的历史结果。完整 GdUnit 编译仍被三个既有 fixture 的 `DisconnectClient` 签名问题阻塞，这些结果不能表述为全套通过。

- [ ] 完成真实服务端昵称审核、拒绝与重试流程，核对保存、重启及跨界面的显示一致性。
- [ ] 在手机上验证输入法、焦点、确认与取消，记录实际客户端、服务端和游戏版本。
- [ ] 单独处理或明确隔离既有 fixture 编译阻塞，提供本轮可追溯的验证记录。

### 开放交互问题

- [ ] #49 在真实界面测试齿轮与气泡的命中区域、遮挡和拖动手势，覆盖鼠标及手机触摸。
- [ ] #32 修复游戏按钮聚焦时按 Enter 误开聊天的问题。验收首次进入时的焦点、键盘／手柄导航、读屏和聊天快捷键。
- [ ] #40 用 PC 房主和 PC／Android 客机复测 LAN 自定义建房、加入、开局及续局。核对 LAN 存档保持 LAN 入口，大厅存档恢复后仍发布大厅房间。
- [ ] #43 收集东尼算法与游戏大厅的确切版本和双端日志，用最小模组组合对照标准与自定义模式。根据复现结果确定修复范围。

## P1 条件项 #51 协议选择

本项排在 P0 稳定性之后。默认行为调整须有对应支持门槛和完整回归，不能只改界面默认值。

- [ ] 新建房间默认选择可用的新协议。新协议不可用时默认选择可用的兼容协议，保留手动切换。两种协议均不可用时显示具体原因。
- [ ] 加入与续局遵守房间及原存档已冻结的协议，不因客户端默认值改变而迁移存档协议。
- [ ] 覆盖旧游戏、旧客户端、缺少必要能力和不支持的组合，确认拒绝原因清晰且不会静默改变协议。

## 后续范围

- #45 的结算页新开一局后移，楼层重置部分已撤回，不纳入本轮实现。
- #47 的跨服房间池后移。后续先设计小范围方案，房间 ID 按服务器命名空间区分，刷新需有界且原子替换，跳转前重验目标房间，聊天连接独立处理。

## 里程碑与执行顺序

| 阶段 | 交付物 | 进入下一阶段的条件 |
|---|---|---|
| M1 复现与取证 | 重开对照矩阵、#48 发送时序与版本日志 | 能区分续局排序、原生重开清理和同成员版本缺口 |
| M2 稳定性收口 | #44／#46 候选回归、#48 根因修复与针对性验证 | P0 自动化完成，进入完整多人及手机验收 |
| M3 条件功能验收 | 昵称、#49、#32、#40，#43 证据结论 | 各项具备独立结果，可据风险决定随版或后移 |
| M4 发布候选 | 固定构建与支持矩阵，完成发布门槛 | P0 全部通过，纳入版本的 P1 逐项通过 |

昵称与界面实测可与稳定性排查并行。#51 在 P0 的真实多人验收通过后实施。P1 按验收结果决定随版或延后。

## 发布门槛

- [ ] P0 对照矩阵具备实际运行证据，角色、槽位、开局与再次保存均正确，未复现的重开反馈有明确结论与剩余风险。
- [ ] 桌面、Android 与承诺支持的混版组合完成真实多人验收，所有未测项逐项标出，不能用 ABI、codec 或隔离 Godot 结果替代。
- [ ] 本次改动相关测试通过，保存绑定、防串档、离开授权、扩展顺序与协议冻结检查保持有效。
- [ ] 纳入发布的 P1 有实机结果，#51 如随版则额外通过协议默认值与旧存档回归。
- [ ] 候选包、安装包内 DLL 与验证日志对应同一构建，记录哈希及游戏／平台版本，正式客户端、服务端和协议版本分别决定是否调整。
- [ ] 发布说明准确列明已交付内容、支持组合与 2→1 等已知边界，通过独立验收后再安排正式发布。
